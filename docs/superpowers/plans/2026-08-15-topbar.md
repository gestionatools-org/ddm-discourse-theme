# Topbar Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a full-width information band above the site header carrying the theme's three destination links and three live figures about the community.

**Architecture:** A Glimmer component tree rendered into core's `above-site-header` plugin outlet, which sits outside `<GlimmerSiteHeader>` in `application.gjs`. Being in normal flow above a sticky header is what makes the band scroll away on its own, so there is no offset to maintain. The figures come from `GET /about.json`, memoised on an Ember service so the request happens once per application instance and the cache dies with it. The three destination links move up out of the header, where they have been hidden below `lg` since v0.10.0 for lack of room.

**Tech Stack:** Discourse theme (`"component": false`), Glimmer `.gjs` components, SCSS with the theme's `viewport` library, QUnit acceptance tests through `rake themes:qunit`.

**Spec:** `docs/superpowers/specs/2026-08-15-topbar-design.md`. Read it before Task 1 — it carries the reasoning this plan only carries the conclusions of.

## Global Constraints

- **pnpm is not on PATH.** Every command goes through `npx pnpm@10.28.0 <cmd>`. Corepack cannot install it — the corporate Fortinet TLS proxy breaks its registry fetch.
- **`npx pnpm@10.28.0 lint` is the only gate that runs locally.** There is no `test` script. The QUnit suite needs a Discourse checkout with Postgres, Redis and an Ember build; it runs in CI only.
- **English for code, comments, identifiers and commit messages.** Spanish only in conversation with the maintainer.
- **Never write a raw media query.** Use `viewport.from(lg)` / `viewport.until(lg)` / `viewport.between(sm, md)`. Breakpoints: `sm` 640px, `md` 768px, `lg` 1024px, `xl` 1280px, `2xl` 1536px. The library is already `@use`d in `common/common.scss` before every `@import`, so it is in scope in any `stylesheets/**` file without importing it again.
- **BEM with standalone `--modifier` classes.** `.topbar.--no-stats`, never `.topbar--no-stats`. State prefixes are `is-` / `has-`. One BEM block per Ember component.
- **`common/common.scss` imports folders only** and holds zero rules. Each folder's `_index.scss` imports its own files. Only `_index.scss` carries the underscore prefix.
- **`settings.yml` holds functional configuration only.** Every user-visible string lives in `locales/en.yml` and `locales/es.yml` and is referenced by i18n key through `themePrefix`. `themePrefix` and the global `settings` object are auto-injected into theme `.gjs` files — never import them.
- **Prefer overriding core CSS custom properties over redeclaring rules.** All colour in this task comes from existing `--ga-*` tokens and core variables. Introduce no new token and no new hex value.
- **Blocks stay on the homepage.** This band is a plugin outlet, not a block — the Blocks API has no header outlet and themes cannot register new ones.
- **`minimum_discourse_version` is `2026.7.0`.** Do not lower it.
- **`main` is production** — the Discourse Cloud instance pulls it. All work lands through a PR with CI green. The branch `feat/topbar` already exists and already carries the spec commits.
- Git identity is set repo-locally to `gestionatools-org` / `desarrollodemedios@espublico.com`. Do not override it.

- [ ] **Step 3: Extract the configured-links helper**

Create `javascripts/discourse/lib/topbar-links.js`:

```js
// The three destination links in the topbar.
//
// Labels are i18n keys and live in locales/*.yml; only the URLs are settings.
// That split is the theme's rule — settings.yml is functional configuration,
// every user-visible string is a translation.
//
// This lives in lib/ rather than inside the component because two callers need
// the same answer: topbar-links.gjs renders the links, and topbar.gjs has to
// know whether any exist to decide whether the band renders at all. Reading the
// same three settings in two places is how the two drift apart.
const LINKS = [
  { key: "topbar.links.academy", url: () => settings.academy_url },
  { key: "topbar.links.demo", url: () => settings.demo_url },
  { key: "topbar.links.first_steps", url: () => settings.first_steps_url },
];

/**
 * The links that have a URL configured, in display order.
 *
 * A link with no URL renders nothing rather than pointing at "#". All three
 * destinations are still being decided, so the empty result is the expected
 * one for now, not a fault.
 *
 * @returns {Array<{key: String, url: String}>}
 */
export function configuredLinks() {
  return LINKS.map(({ key, url }) => ({ key, url: url()?.trim() })).filter(
    (link) => link.url
  );
}
```

import { configuredLinks } from "../lib/topbar-links";
import TopbarLinks from "./topbar-links";

export default class Topbar extends Component {
  @service router;

  // band of community links is noise on top of a different chrome. Same test

- [ ] **Step 3: Write the service**

Create `javascripts/discourse/services/site-stats.js`:

```js
import { tracked } from "@glimmer/tracking";
import Service from "@ember/service";
import { ajax } from "discourse/lib/ajax";

/**
 * Site-wide figures for the topbar, from /about.json.
 *
 * The same endpoint core's own /about route reads. There is no client-side
 * About model to go through — the old models/about.js no longer exists — and
 * visibility is not gated: Guardian#can_see_about_stats? returns true
 * unconditionally.
 *
 * A service rather than a module-level `let cached`, because the memo has to
 * live exactly as long as the application instance. A module-scope cache lives
 * as long as the module, which in a QUnit run is the whole suite: the first
 * test to resolve /about.json would pin its response for every test after it,
 * and the failure cases — the ones worth testing — would be unreachable.
 */
export default class SiteStats extends Service {
  // The `about.stats` object once it arrives, null otherwise.
  @tracked stats = null;

  // True once the request has settled, whether it produced data or not. This
  // is what separates "still loading" from "failed"; the topbar collapses on
  // the second and not the first.
  @tracked loaded = false;

  #request;

  /**
   * Load the figures once. Idempotent: repeated calls return the same promise,
   * so route transitions never refetch.
   *
   * The rejection is memoised along with the success. On a login-required site
   * an anonymous or 403 response must not turn into a request on every
   * navigation.
   *
   * @returns {Promise}
   */
  load() {
    this.#request ||= ajax("/about.json")
      .then((result) => (this.stats = result?.about?.stats ?? null))
      .catch(() => (this.stats = null))
      .finally(() => (this.loaded = true));

    return this.#request;
  }
}
```

- [ ] **Step 4: Write the figures component**

Create `javascripts/discourse/components/topbar-stats.gjs`:

```js
import Component from "@glimmer/component";
import { service } from "@ember/service";
import I18n, { i18n } from "discourse-i18n";

// Members plus two 30-day windows, not lifetime totals. Zapier can show
// lifetime figures because theirs are in the tens of thousands; this is a
// closed community around a certification programme, where the totals are
// three or four figures and read as an empty forum. Recent activity reads as a
// live one.
const FIGURES = [
  { key: "topbar.stats.members", stat: "users_count" },
  { key: "topbar.stats.topics", stat: "topics_30_days" },
  { key: "topbar.stats.active", stat: "active_users_30_days" },
];

export default class TopbarStats extends Component {
  @service siteStats;

  constructor() {
    super(...arguments);
    this.siteStats.load();
  }

  get figures() {
    const stats = this.siteStats.stats;

    if (!stats) {
      return null;
    }

    // A key core stops serializing degrades to one missing figure rather than
    // to "NaN members".
    return FIGURES.map(({ key, stat }) => ({ key, count: stats[stat] }))
      .filter(({ count }) => Number.isFinite(count))
      .map((figure) => ({
        ...figure,
        // I18n.toNumber, not core's number() from discourse/lib/formatter:
        // that one abbreviates everything past 999, so a users_count of 1240
        // would render "1.2k". Core wants that in narrow topic-list cells. The
        // band has room, and this is the one lifetime total on display.
        value: I18n.toNumber(figure.count, { precision: 0 }),
      }));
  }

  <template>
    {{#if this.figures}}
      <ul
        class="topbar-stats"
        aria-label={{i18n (themePrefix "topbar.stats.aria_label")}}
      >
        {{#each this.figures as |figure|}}
          <li class="topbar-stats__figure">
            <span class="topbar-stats__value">{{figure.value}}</span>
            <span class="topbar-stats__label">
              {{i18n (themePrefix figure.key) count=figure.count}}
            </span>
          </li>
        {{/each}}
      </ul>
    {{/if}}
  </template>
}
```

- [ ] **Step 5: Teach the container about the figures**

Replace the body of `javascripts/discourse/components/topbar.gjs` with:

```js
import Component from "@glimmer/component";
import { service } from "@ember/service";
import { configuredLinks } from "../lib/topbar-links";
import TopbarLinks from "./topbar-links";
import TopbarStats from "./topbar-stats";

export default class Topbar extends Component {
  @service router;
  @service siteStats;

  // `above-site-header` renders on every route, including /admin, where a
  // band of community links is noise on top of a different chrome. Same test
  // core's own `isCurrentAdminRoute` uses.
  get onAdminRoute() {
    return this.router.currentRouteName?.startsWith("admin");
  }

  get hasLinks() {
    return configuredLinks().length > 0;
  }

  // `loaded &&`, never a bare `!stats`. While the request is in flight the band
  // renders and reserves its height, and the figures appear inside it. Treating
  // "loading" as "unavailable" would make the band absent on mobile and then
  // push the whole page down when the request landed.
  get statsUnavailable() {
    return this.siteStats.loaded && !this.siteStats.stats;
  }

  get visible() {
    return !this.onAdminRoute && (this.hasLinks || !this.statsUnavailable);
  }

  <template>
    {{#if this.visible}}
      <div class="topbar {{if this.statsUnavailable '--no-stats'}}">
        {{! `wrap` is core's own container class: it applies --d-max-width and
            the page gutters, and widens itself on sidebar pages. Reusing it is
            what keeps the band's left edge on the header logo at every page
            shape. }}
        <div class="wrap">
          <TopbarLinks />
          <TopbarStats />
        </div>
      </div>
    {{/if}}
  </template>
}
```
